## 本机订单读取基线

2026-11-20。本机 Docker Desktop Linux VM 为20个 vCPU、15.51 GiB共享内存，Docker 29.7.2。Spring Boot 3.5.16、Java 21、MySQL 8.4.7、Redis 7.4.6，启用 JSON 请求日志与 Prometheus。实际应用镜像 `sha256:475a7225023c037c8d609c1adf1913fb309a1e0dbc353c335b0da2195e97759c`，修订 `a135325`。此后 `0850bb2` 只修改工作流及手册。

[测量脚本](../../project/deploy/compose/measure-orders.mjs)从宿主 Node 22.20.0 经回环连接访问容器。用已存在的普通录单员及其一条可见订单，保持数据不变。先预热30次，再做三轮，每轮240次，6个并行 worker。请求固定为 `GET /api/v1/orders?page=1&size=20`。延迟包括响应读取与 JSON 解析，p95 按最近秩计算，成功判定包含返回结构和一致总条数。

| 轮次 | 请求 | 失败 | p50 ms | p95 ms | p99 ms | 成功请求每秒 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 240 | 0 | 12.52 | 19.39 | 21.85 | 445 |
| 2 | 240 | 0 | 8.04 | 10.95 | 12.75 | 719 |
| 3 | 240 | 0 | 6.97 | 9.69 | 10.89 | 822 |

从[监控演练](../../project/deploy/compose/RECOVERY.md)启用的本机实例复现。将 `CAPSTONE_BASE_URL` 指向该实例，设置 `CAPSTONE_BENCH_USER` 和 `CAPSTONE_BENCH_PASSWORD` 为有可见订单的演练录单员，运行 `node project/deploy/compose/measure-orders.mjs`。本结果只覆盖单容器、单条可见订单和短时读路径。生产容量评估需要另行测量真实数据量、并发写入、持续流量和网络开销。

## 发现与修复

- 自然过期和刷新丢失后，客户端重试使用轮换后的凭据或要求重新登录。[会话回归](P6-03-B.md)
- 订单请求未完成前锁定面板切换，保留写入成功后的列表更新。前后端按同一 Unicode 规则裁剪客户名称。[双轴复核](../reviews/P6-03-C.md)
- 数据源断开时，登录事务打开失败由错误处理器返回脱敏500及请求ID。恢复只导入校验通过的副本，并验证两个会话表归零。[恢复与故障记录](P6-04-B.md)

本次工作区依赖审计按 high 门槛通过，记录2个 low、9个 moderate。外部发布及更大负载的验证属于后续工作。
