# P5 综合练习 · 从消息重投到应用回滚

适用第38至41章。使用实验说明中的一次性服务、卷和kind集群。

| 操作 | 通过条件 |
|---|---|
| 运行[可靠消息实验](../08-cloud-native/38-messaging.md)，让同一消息在提交后重投，再投递无法正常处理的消息。 | 重投和并发消费只提交一份业务结果，毒消息可从死信队列观察。 |
| 运行[事务Outbox实验](../08-cloud-native/39-distributed-reliability.md)，在提交后使消息发布失败，再恢复代理。 | 业务与Outbox记录已经提交，故障恢复后消息可送达，重复投递后消费副作用仍只有一次。 |
| 运行[Compose停止实验](../../project/deploy/compose/TEACHING.md)，按驱动顺序观察数据库故障和在途写入。 | 失库时就绪503、存活200。SIGTERM后释放已有写锁，在途请求返回200，数据库提交与审计记录相符，重启仍可读取。 |
| 运行[Kubernetes探针与滚动实验](../../project/deploy/k8s/TEACHING.md)，观察Service端点和旧Pod退出。 | 失库时就绪端点撤除，恢复后重新接流。滚动替换期间集群内探测无失败，旧Pod退出状态被记录。 |
| 运行[交付与回滚实验](../08-cloud-native/41-continuous-delivery.md)，核对扫描报告和发布历史。 | 两份演练镜像通过扫描门禁。升级前后和回滚后的版本标记可核对，两次切换的探测请求均无失败，回滚后用原会话刷新并读取原任务。 |

任选三项说明机制：发布确认与消费提交的关系、Outbox租约过期后为何仍需去重、就绪探针与存活探针的职责、应用回滚与数据库迁移的关系。提交每个场景的命令、预期、实际结果和日志路径。提交记录前移除凭据与刷新令牌。
