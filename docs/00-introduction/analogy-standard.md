# 教学写作与类比规范

本规范落实[实施计划](../../JAVA-FOR-NESTJS-IMPLEMENTATION-PLAN.md)第2、7节，不改变课程范围、章节目录或技术基线。适用于作者、示例实现者和独立审查者。

## 作者从哪里开始

1. 从[课程目录](../course/index.md)确认章节和先修知识，阅读[兼容矩阵](compatibility-matrix.md)。
2. 将[章节模板](../templates/chapter.md)复制到计划规定的`docs/<part>/<nn>-<slug>.md`。例如第18章使用`docs/04-spring-boot/18-spring-ioc.md`作为候选路径；P0-07建立映射后以映射中的实际路径为准。
3. 先列出独立知识点，再为每个知识点复制模板中的完整十段。不要只在章首写一个统一故事。
4. 按[双端代码模板](../templates/code-comparison.md)先定义可比较的输入、输出和错误语义，再实现、运行、记录。
5. 为每个核心知识点填写[类比评分表](../templates/analogy-review.md)，执行本页章末DoD，提交证据供独立审查。

模板中的`【待填写】`、示例路径和注释代码都不是实现成果。复制后必须填实或明确说明不适用原因；不得把未实现命令或未执行结果写成通过。

## 知识点怎样划分

一个知识点应能够单独回答“解决什么问题、参与者如何协作、边界是什么、怎样验证”。一个小标题若同时覆盖多个机制，应继续拆分；一个知识点只剩语法名词、没有可解释行为时，应补充问题与机制。

以计划中的IoC样章为例，Bean定义、组件扫描、构造器注入、作用域、生命周期、循环依赖和容器启动是不同知识点，不能共享一份章首类比后省略各自边界。

每个`###`教学知识点有稳定ID，如`ch18-kp01`。章节元信息、参考资料、答案等辅助区域用`##`，避免将辅助标题混同知识点。ID命名是模板约定，P0-07再建立自动结构与映射检查。

## 十段的固定顺序

| 序号 | 段落 | 必须回答 |
|---|---|---|
| 1 | 一句话定义 | 是什么？尽量60字内，先准确再简短 |
| 2 | 为什么需要它 | NestJS开发者熟悉的什么问题引出该机制？ |
| 3 | 生活类比 | 哪些角色、动作、关系相对应？哪里失效？ |
| 4 | Node.js / TypeScript / NestJS技术对照 | 部分可比，还是无直接等价物？为何？ |
| 5 | 两端代码对照 | TS/Nest端先、Java/Spring端后；真实路径、依赖、命令和输出在哪里？ |
| 6 | 原理与流程图 | 实际执行顺序、生命周期、线程/代理/数据流是什么？ |
| 7 | 类比边界与错误直觉 | 相似、不相似和不能推出的结论分别是什么？ |
| 8 | 企业应用场景与选型 | 何时用、何时不用、替代方案和代价是什么？ |
| 9 | 常见错误与排查 | 怎样触发、观察、定位、修复和回归？ |
| 10 | 实操练习与验收 | 基础题、迁移题、思考题各验证什么？通过条件是什么？ |

使用模板中的`####`标题保留该顺序。复杂机制采用Mermaid或独立SVG；简单机制可用准确文字顺序，解释为何无需图，不为了形式加入无信息图表。

## 类比必须带映射和边界

先给现实直觉，再说明精确机制。至少记录“角色/动作/关系→技术对象/行为”的映射清单，并写出一条会让类比失效的条件或反例。

实施计划的餐厅IoC示意可以帮助理解集中供给依赖，但不能据此推断Spring Bean与Nest Provider的作用域、可见性、生命周期和代理行为一致。审查应追问这些机制差异的代码或资料证据。

不要使用“完全相同”“就是Java版XX”等没有边界的结论；也不能为了类比相似，刻意改写任一生态的惯用实现。安全、事务和并发的因果说明必须来自机制与验证，故事不能替代证明。

## 没有准确类比时怎么写

**没有技术对应物**：第4段明确写“无直接等价物”，指出读者最容易误认的概念与关键差异。第5段仍保留两端栏目：TS端可以展示相关问题或反例；若没有合理代码，说明原因并给出可检查资料，不能生造一个看起来同名的实现。Java端照常提供适用的示例与验证。

**生活类比不准确**：第3段保留，填写“以小模型/反例替代生活类比”，说明故事会掩盖什么机制，再列参与者、状态、执行规则和失效条件。第7段继续记录模型边界。审查仍按清晰、准确、映射、边界和迁移效果评估，不为凑故事而降低准确性。

**无需新增代码**：按原计划说明原因和可检查的资料或复现练习。不能把“不新增代码”变成整章没有可验收证据。

## 示例与证据的最低要求

- 完整代码必须有仓库运行物；片段注明上下文、未展示部分和定位方式。
- 同题对照明确共享业务语义、允许差异及原因。负例应验证预期失败，不将故意失败的程序直接冒充应当全绿的构建。
- 命令注明工作目录、环境版本、前置服务和退出条件。Windows/Linux步骤不同就分别记录，不把某一环境通过扩写成所有平台通过。
- 路径、测试和运行命令在实现后填写；没有执行时写“未执行＋原因”，不要编造日志、截图或读者反馈。
- 版本受兼容矩阵约束，跨版本特性注明适用范围。重大调整先提交ADR并更新计划。

## 类比评分与独立审查

五项各0~2分，总分10分，具体锚点见[评分表](../templates/analogy-review.md)。核心知识点建议达到8/10；**技术准确性或边界为0直接不通过**，不受总分影响。

分数是辅助，不替代技术事实、代码运行或教学效果核验。作者自检和独立审查分开记录；证据不足就记为证据不足，不能先给通过。此模板交付也不表示后续样章已经完成独立Review。

## 单章Definition of Done

- [ ] 知识点完整拆分，章节范围和先修明确。
- [ ] 每个知识点都有定义、动机、生活类比或说明理由的小模型、技术对照和边界。
- [ ] 同题代码可构建，关键输出有测试、日志或可检查记录。
- [ ] 核心链路有机制解释，复杂机制有流程图。
- [ ] 有企业场景、反例或常见错误及排查方法。
- [ ] 练习和验收标准明确，答案/提示放在练习之后。
- [ ] 版本、依赖、运行环境和官方资料可追溯。
- [ ] 无断链、概念冲突与明显文字问题。
- [ ] 独立Review通过，有审查者、发现、修订及结论记录。
- [ ] 目录、章内导航、章节映射和进度同步更新。

P0-07尚未交付的自动检查工具不能算作已经执行。模板只规定待填写内容；最终合并仍要求适用CI与独立验收通过。
